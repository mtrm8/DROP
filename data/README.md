# Bunker data pipeline

`npm run bunker:fetch` queries API-Football (API-Sports v3) for today's not-started fixtures, recent historical results, confirmed or projected lineups, season statistics for starting players and the `Goals Over/Under → Over 2.5` market. It requires `API_FOOTBALL_KEY` and writes private working input to ignored `data/bunker-live.json`. `BUNKER_TIMEZONE` defaults to `Asia/Jerusalem` and defines "today"; `BUNKER_LEAGUES` optionally selects comma-separated league IDs (default: 39, 61, 78, 135, 140). The search covers *all fixtures in these leagues today* and all provider-returned bookmakers; it cannot guarantee the best price outside the provider's coverage. Availability of odds, lineups and player season stats depends on the provider's coverage and subscription.

The selector requires at least three home/away results per team from the past year and season stats for at least nine starters per side. It uses confirmed XIs when available; otherwise the last starting XI is marked **projected**, never confirmed. A confirmed XI with more than four changes from the previous XI is excluded. Odds must have been updated **today**, be no more than 12 hours old at build time, and both legs must come from the **same bookmaker**. Each leg and the combination require at least 4% modeled expected return. Goals/assists, minutes, shots and key passes appear as player context; the Poisson model uses historical goals, not an uncalibrated player-strength adjustment. If no pair qualifies, the job publishes a fresh dated "no selections today" report. Odds are a **daily price snapshot**, not a live quote: the browser hides picks when a fixture starts or the report date is no longer today.

`BUNKER_DATA_FILE=data/bunker-live.json BUNKER_REQUIRE_LIVE=1 npm run bunker:generate` validates the fetched input and writes `components/bunker/generatedReport.json`. `npm run build:static` exports to `out/`; `npm run bunker:test` verifies the model and selection rules. `npm run build` uses the synthetic local demo input by default; it **must not** be used for live publication.

The installed GitHub Actions workflow `.github/workflows/bunker.yml` runs **once a day** at 12:15 UTC (14:15/15:15 in Israel) and publishes `out/` to the `gh-pages` branch. There is no shorter interval: each run rebuilds the whole report from that day's fixtures. `node scripts/bunker-model.mjs` remains a compatibility entry point that fetches, validates, builds `out/` and mirrors it into `public/`; importing the model from tests or other scripts does **not** trigger publication. If the provider cannot be reached, the run publishes a **dated** "scan did not complete" report for the current day instead of aborting, so the site never keeps serving a previous day's matches. Genuine build failures still abort publication. `scripts/postbuild-pages.mjs` also exports `out/bunker-data.json`, which an already-open Bunker checks every five minutes without reloading or resetting access.

Automated publication (`BUNKER_REQUIRE_LIVE=1`) requires real provider data that describes the **current local day** in the report's timezone and contains only fixtures that have not kicked off. It deliberately does *not* require a recent timestamp: a sequential scan of every fixture routinely runs far longer than the fifteen-minute window an earlier version imposed, and enforcing that window aborted long scans and left the site showing the previous day's report.

The Bunker shows the report as a **daily snapshot**, and expires it per match rather than as a whole: once one of today's matches kicks off it is dropped from the list, while any sibling match that has not started yet stays visible and actionable. A report is labelled by its own scan date, and the page distinguishes four different situations rather than showing one vague "waiting for data" message: today's scan is ready, today's scan finished without qualifying selections, today's scan could not be completed, or the published report belongs to an earlier day. Each one names the time of the next daily run. An open tab that polls `bunker-data.json` also replaces a report that has nothing to show when a recovered scan arrives, so a transient outage clears itself on the next successful build.

The checked-in input is **synthetic demo data**, not historical results. The report labels it as such. As an alternative to the built-in fetcher, `BUNKER_DATA_URL` (optional `BUNKER_DATA_TOKEN` bearer token) or `BUNKER_DATA_FILE` can supply a prepared JSON payload with this schema:

```json
{
  "mode": "live",
  "source": "Verified provider / dataset name",
  "asOf": "2026-09-26T12:00:00Z",
  "combinedOdds": 2.32,
  "picks": [],
  "results": []
}
```

For a report with picks, supply at least three **home** results for each home team and three **away** results for each away team, plus future kickoff, an `Over 2.5` price no more than twelve hours older than `asOf`, `lineup.homeKind`/`awayKind` (`confirmed` or `projected`) and `players` summaries for nine starters on each side. A starting XI is taken from the most recent of the last five results that actually published one, so a single fixture with missing lineup data no longer discards the day. `asOf` must fall on the current local day in the report's `timeZone` for automatic publishing. Use exact team names in `picks` and `results`.

Selection is a **same-bookmaker accumulator search**, and the bar applies to the combination, not to each leg: legs are only required to be individually positive, and the search ranges over two to four legs, keeping whichever combination has the highest expected value. Requiring every leg to clear 4% on its own was stricter than the maths needs — a real book rarely offers two legs at 4% each — and was the main reason flat days published nothing. The default league pool spans twelve competitions rather than five, because value on a given day is often outside the biggest five. Prices must still be no more than twelve hours old, but no longer have to be stamped on the same calendar day, because the provider's update stamps lag fixture time by hours.

When no combination reaches the 4% combined edge, the report is **not** padded with picks that do not qualify. Instead every eligible fixture is remembered as it is scanned, and the report carries a `watchlist` of up to five matches so the page always shows today's football rather than a blank screen. Modelled matches come first, ordered by how close they came, each with its real signed edge. The list is then topped up with the day's remaining **soonest** fixtures, which keep whatever live data was collected — an `Over 2.5` price where one was quoted — and a `note` naming the data gate that dropped them (`אין מחיר עדכני`, `אין נתוני שחקנים מלאים`, and so on). A fixture that never reached the model carries no probability, no fair odds and no edge, and says so rather than borrowing a number. The page labels the section as a watchlist, never as a recommendation.

The report also carries a `scanNote` stating how many fixtures were eligible, how many were evaluated and why the rest were dropped, so "nothing qualified" is distinguishable from "nothing could be evaluated" and from "there were no matches today".
 Data preparation, licensing, odds availability and opponent-strength adjustments depend on the upstream provider. The model takes the average of home goals scored and away goals conceded for the host's Poisson mean, and the converse for the visitor; it assumes independence between fixtures for accumulator probability. The combined price is a two-decimal rounding of one bookmaker's leg product, **not an independently verified offered accumulator price**. `goalBuckets` groups six or more goals in its final bin.

Configure repository secret `API_FOOTBALL_KEY` and optional variable `BUNKER_LEAGUES`, enable Actions with write access to repository contents, and keep GitHub Pages set to the `gh-pages` branch root. The generated client JSON is public: **never put API tokens or private data in source fields**.
